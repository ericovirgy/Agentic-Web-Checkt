# 03 — Competitive matrix: "Is this website usable by / ready for AI agents?"

Research date: 2026-10-04. Scope: open-source projects and commercial products that evaluate whether a **website** (not a repo, not an API-only service) is ready for AI agents. Repo-level "agent readiness" tools (microsoft/agentrc, uinaf/agent-readiness, @kodus/agent-readiness, dahoai/agentready) are explicitly out of scope.

> **Refresh 2026-10-05 — does the positioning still hold? Yes.** Re-checked every row on npm/GitHub plus new searches (details in section F at the end). Nothing new executes browser tasks on arbitrary websites and attributes verdicts to page defects: the behavioural layer is still only ora/ax `deep-journey` (hosted, curated, unchanged since 2026-09-17) and Netlify AXIS (ACP coding-agent harness, no browser). Two things did move: (1) **ora.ai + Vercel published the "AgentReady" open standard v1.0 (Aug 2026) with a public dataset of 1,033 real agent runs on 25 product sites** — the first paired signals×outcomes dataset, but fetch-based coding agents on dev-platform tasks, and its `AR-ACT-*` rules only cover API/MCP/SDK/CLI, not UI; (2) a July-2026 arXiv paper (2607.12056) shows a controlled 49.3%→89.3% agent task-success lift from site-side changes (see file 04). Both strengthen, rather than threaten, the "finish the job + safe to let them" positioning. New entrants since the baseline are all static (ai-readiness-check, startuphub.ai, santos-audit-api [browser-rendered Lighthouse/axe deep audit, paid], ainative AX Audit, webmcp-checker.com); the 301.st "Agent Readiness Inspector" extension turned out to be open source. Lighthouse 13.5.0, Playwright 1.63.0, @playwright/mcp 0.0.83, chrome-devtools-mcp 1.10.1 are unchanged.

## Method and evidence labels

- **FACT** = read directly from the cited page (GitHub repo page, raw `package.json` / `pyproject.toml` / source file on raw.githubusercontent.com, npm registry JSON) or from a primary vendor page.
- **FACT (secondary)** = the primary page was blocked by the network proxy in this session (blog.cloudflare.com, developer.chrome.com, vercel.com, netlify.com, isitagentready.com, is-agentic.com, huggingface.co, glama.ai, docs.squirrelscan.com, higoodie.com) so the number/claim comes from a reputable secondary page named in the cell.
- **UNVERIFIED** = README claim not corroborated by source, or a page that could not be fetched.
- GitHub's search API and github.com/search were blocked, so discovery used web search + npm registry search (`registry.npmjs.org/-/v1/search`), then each candidate's repo page, commit log and manifests were fetched individually.
- Star counts are as rendered on the repo page on 2026-10-04 and are approximate.

Capability columns used in the matrix:

| Code | Meaning |
|---|---|
| **D** | Deterministic static checks (robots/llms.txt/sitemap/JSON-LD/markdown negotiation/manifests…) |
| **B** | Behavioural: runs a real agent/LLM through tasks on the site in a browser |
| **R** | Renders with a real browser (Chrome/Playwright/Puppeteer) rather than fetch+parse |
| **S** | Security / safety-for-agents review (prompt-injection surface, unguarded actions, bot walls, Web Bot Auth) |
| **Sc** | Produces a score / grade |
| **CI** | Ships a GitHub Action or documented CI gate |
| **Bd** | Produces a badge |
| **Bm** | Publishes a benchmark / leaderboard of real sites |
| **OSS** | Scanner logic itself is open source (not just a thin client to a hosted API) |

## C. What we should NOT duplicate

1. **Another fetch+cheerio checklist scanner with a 0–100 score.** Lighthouse, Cloudflare and Vercel own the definition of "agent-ready" and at least 15 OSS tools already implement it; marginal value is zero and the standards they check are still moving (ARD `ai-catalog.json`, Content Signals, Web Bot Auth, UCP/ACP).
2. **llms.txt generation or validation.** Generation is a commodity (Mintlify, Firecrawl, framework plugins); validation is in Lighthouse itself.
3. **WebMCP validity audits.** Lighthouse ships three; `webmcp-evals` covers tool-calling tests.
4. **Yet another incompatible score scale.** If a deterministic layer is needed, *consume* Lighthouse's `agentic-browsing` JSON (and optionally Cloudflare/Vercel reports) rather than re-implementing their checks; map to their IDs.
5. **GEO/AEO citation tracking** ("does ChatGPT cite me?") — geo-optimizer (992★), Canonry, MaxAEO, etc. own that lane.
6. **Repo-level agent readiness** (AGENTS.md, boot scripts) — different market, already served by microsoft/agentrc, uinaf, kodus, dahoai.

## D. Conclusion: where the real gaps are

Honest assessment: **deterministic agent-readiness auditing is a mature, crowded category as of October 2026.** Google Lighthouse has an official (if unscored) "Agentic Browsing" category in Chrome 150, Cloudflare and Vercel run public scanners with published spec/levels, and ForkPoint/agent-lighthouse already uses the exact "Lighthouse for AI agents" positioning with a GitHub Action, badge, MCP server and 200+ checks. Nothing in that layer is worth re-building.

What the ecosystem still lacks:

1. **An open behavioural layer.** Every tool measures *signals* (files, headers, markup) and none measures *outcomes*. The only product that runs real agents on a site is ora/ax, and it is closed, hosted, quota-limited and curated-task only. Netlify AXIS is the right shape (scenario → run agent → graded transcript) but has no browser harness, no site-generic task archetypes, and judges with an LLM rubric rather than verifiable task assertions. Site owners therefore cannot answer "can an agent actually find my pricing / submit my contact form / add to cart / reach the docs for feature X on my site, how many steps and tokens does it burn, and what page defect made it fail?"
2. **A site-owner-facing agent-safety review.** Nothing scans a site for the things that make it unsafe for an agent to *act* on: hidden-text / aria-hidden / HTML-comment instruction injection, WebMCP tools or forms that mutate state without confirmation or auth, bot walls that silently serve the app shell (Vercel's "agent-friendly 404" is the only adjacent check), and absence of Web Bot Auth / rate-limit behaviour toward agent user-agents. Only consumer extensions and MCP-server scanners touch this.
3. **Validation.** No one has shown that any static score predicts agent task success. A paired dataset (static signals × behavioural outcomes across a few hundred sites) does not exist and would make whichever tool publishes it the reference.
4. **Failure attribution.** Static tools say "llms.txt missing"; behavioural runs say "task failed"; nobody links a failed agent trajectory back to the concrete page defect (cookie wall, CSR-only content, unlabeled button, infinite scroll, CAPTCHA), which is what a developer needs to fix.

### Recommended product gap to pursue

Build the **behavioural + safety layer on top of Lighthouse's agentic-browsing category, not beside it**:

- **Deterministic layer = import, don't re-implement.** Run Lighthouse (`--only-categories=agentic-browsing`, plus a11y/SEO as needed) and ingest its JSON; optionally ingest Cloudflare / Vercel / Scovant reports. Add only the handful of deterministic checks none of them have (agent-UA vs. human-UA response diff, bot-wall/app-shell detection, hidden-instruction scan).
- **Behavioural layer = the product.** A Playwright-based runner with pluggable agent backends (local/open models included, to control cost) executing a fixed library of **site-generic task archetypes** (find price, find contact/support path, locate a specific doc, complete a form, add to cart/checkout to the last safe step, log-in flow up to credential entry) with **verifiable assertions** (URL reached, element state, extracted value) instead of LLM-judged rubrics. Output per task: success, steps, tokens, wall-time, cost, and a **failure-attribution tag** mapped to a page defect and to a Lighthouse audit ID when one exists. Multiple runs + a deterministic "smoke" mode (as webmcp-evals does) to tame non-determinism.
- **Safety layer.** Hidden-instruction / prompt-injection surface report, unguarded-mutation detection for forms and WebMCP tools, agent-UA access-policy diff, Web Bot Auth / Content Signals presence. This is the piece no site-owner tool offers.
- **CI action + badge keyed on behavioural results** ("agents complete N/M tasks"), not on a checklist score — this is a genuinely new signal and is table-stakes packaging, not differentiation.
- **Public benchmark** that pairs static (Lighthouse) with behavioural outcomes on a few hundred sites, published early, to establish the correlation (or lack of it) and the tool's credibility.

Positioning in one line: *Lighthouse tells you whether agents can read your site; this tells you whether agents can finish the job on it, and whether it is safe to let them.*

Biggest risks: LLM run cost and flakiness (mitigate with cached trajectories, local models, smoke mode, N-of-M runs), and ora/ax open-sourcing or Google adding task-based audits to Lighthouse (mitigate by being the open, backend-agnostic reference implementation and owning the task-archetype library and the benchmark).
