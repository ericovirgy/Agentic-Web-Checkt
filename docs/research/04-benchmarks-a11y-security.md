### B.2 "Accessibility tree" as the agent's observation

- **Chrome DevTools MCP** `take_snapshot`: "Take a text snapshot of the target page based on the a11y tree. The snapshot lists page elements along with a unique identifier (uid)"; `click`, `fill`, `hover`, `drag`, `fill_form` take uids. FACT (https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/main/docs/tool-reference.md)
- **Playwright MCP** `browser_snapshot`: accessibility tree with `ref`s, advertised as "Fast and lightweight. Uses Playwright's accessibility tree, not pixel-based input", "LLM-friendly. No vision models needed", "Deterministic tool application"; `--caps vision` adds `browser_mouse_click_xy` for canvas/custom UIs. FACT (https://github.com/microsoft/playwright-mcp)
- **browser-use** (`browser_use/dom/service.py`): merges CDP `DOMSnapshot.captureSnapshot` (styles, paint order, bounds), `DOM.getDocument`, and `Accessibility.getFullAXTree` into `EnhancedDOMTreeNode`; interactivity = semantic tags/roles (`ClickableElementDetector.is_interactive`) + `getEventListeners()` click/pointer handlers (capped at 100 elements) + `tabindex` + cursor/bounds; visibility excludes `display:none`, `visibility:hidden`, `opacity≤0`, with a `viewport_threshold` (default 1000px); `DOMTreeSerializer` assigns sequential numeric indexes in paint order that the LLM uses as action targets, keeping XPath + backendNodeId; iframes recursed (`max_iframe_depth` 5, `max_iframes` 100, cross-origin optional), shadow roots traversed. FACT (https://raw.githubusercontent.com/browser-use/browser-use/main/browser_use/dom/service.py)
- **Stagehand** `observe()`: natural-language query → list of real selectors + descriptions (+ suggested method/args), built on "hybrid accessibility-tree trimming"; `act()` and `extract()` complete the trio. FACT (https://github.com/browserbase/stagehand)
- **BrowserGym**: `axtree` observation with `bid` attributes is the canonical research representation (see A.1). FACT
- **Modality research**: a11y-tree extraction is ~50–200 ms and 2k–10k tokens; DECEPTICON shows a11y-only agents are *less* manipulable by visual dark patterns but complete fewer tasks; EntWorld-style enterprise papers find a11y-only inadequate where metadata is incomplete, screenshot+tree strongest; some studies find adding screenshots to a11y tree changes little. FACT\* (arxiv 2512.22894, 2601.17722; prophetchrome.com/blog/accessibility-tree-vs-screenshots-browser-ai). ## C. Agent security on websites

### C.1 Threat framing

- **OWASP LLM01:2025 Prompt Injection** distinguishes direct vs indirect injection ("external sources (websites, files) contain content that, when processed, alters the model's behavior"); Scenario #2 is hidden instructions in a web page triggering exfiltration during summarization; mitigations: constrain behaviour, validate output format, input/output filtering, least privilege, **human approval for high-risk operations**, **segregate and clearly identify external/untrusted content**, adversarial testing. FACT (https://raw.githubusercontent.com/OWASP/www-project-top-10-for-large-language-model-applications/main/2_0_vulns/LLM01_PromptInjection.md)
- **OWASP Top 10 for Agentic Applications (Dec 2025)**: ASI01 Agent Goal Hijack, ASI02 Tool Misuse and Exploitation, ASI03 Identity and Privilege Abuse, ASI04 Agentic Supply Chain, ASI05 Unexpected Code Execution, ASI06 Memory & Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures, ASI09 Human-Agent Trust Exploitation, ASI10 Rogue Agents; preceded by the "Agentic AI – Threats and Mitigations" guide. FACT\* (https://genai.owasp.org/)
- **WebMCP spec, Security & Privacy Considerations**: names *tool poisoning* (instructions in tool name/description/schema), *output injection* (tool return values treated as trusted), *misrepresentation of intent* (declared vs actual behaviour; authenticated sessions let tools do purchases/transfers without re-auth), over-parameterised tools as a fingerprinting/privacy channel, same-origin and private-browsing boundaries. Mitigations: `Permissions-Policy: tools=()`, 128-char tool-name limit, shared injection eval datasets, annotations `readOnlyHint`, `untrustedContentHint`, **`consequentialHint`** ("agents and user agents can selectively enforce mandatory user confirmation prompts before executing high-stakes tools"). FACT (https://raw.githubusercontent.com/webmachinelearning/webmcp/main/index.bs; rendered at https://webmachinelearning.github.io/webmcp/#security-privacy)

### C.2 Incidents, vendor numbers and defenses

- **Brave vs Perplexity Comet** (disclosed 2025-08-20; reported 2025-07-25, fixed by 2025-08-13): "Summarize this page" fed page text to the LLM without separating it from user intent; instructions hidden as white-on-white text, HTML comments, or in a Reddit spoiler/comment; chain exfiltrated the user's Perplexity email and a Gmail OTP with no user interaction. Brave's recommendations: separate user instructions from page content, treat page content as untrusted, require confirmation for security-sensitive actions, isolate agentic browsing from regular browsing. FACT\* (https://brave.com/blog/comet-prompt-injection/; https://www.theregister.com/2025/08/20/perplexity_comet_browser_prompt_injection/)
- **Anthropic Claude for Chrome** (2025-08-26 preview): 123 cases / 29 scenarios; ASR 23.6% → 11.2% with mitigations; browser-specific challenge set 35.7% → 0%; mitigations: site-level permissions, **confirmation before "publishing, purchasing, or sharing personal data"** (kept in autonomous mode), blocked categories (financial services, adult, pirated content), classifiers for suspicious instructions. Red-team example: malicious email induced Claude to delete the user's emails. FACT (https://claude.com/blog/claude-for-chrome). ### C.3 Hidden-text / invisible-instruction heuristics (site-side detectable)

Techniques catalogued across Brave, PhantomLint and detector tools: `display:none`, `visibility:hidden`, `opacity:0`, `font-size:0`/tiny fonts, text colour == background, off-screen positioning (`left:-9999px`, `clip`/`clip-path`, zero-area boxes), z-index burial, `hidden` attribute, `aria-hidden="true"` text, HTML comments, `<noscript>`, alt/EXIF text, zero-width/Unicode-tag characters, base64/ROT13. PhantomLint's principled method: diff normally-extracted text against OCR of the rendered page; mismatches go to a prompt detector; 3,402 docs, 0 false positives on negatives, found all 113 hidden prompts. FACT\* (https://arxiv.org/abs/2508.17884; search summaries). INFERENCE for checks: extract text from nodes that are (a) absent from the rendered a11y tree or (b) hidden by computed style, then flag imperative/LLM-addressed phrasing ("ignore previous instructions", "you are an AI", "assistant:", tool-call syntax).

### C.4 Destructive / consequential action taxonomy (synthesis)

INFERENCE from the vendor policies above: irreversible or externally visible = **purchase/pay/transfer**, **send/publish/post/share**, **delete/cancel/unsubscribe**, **grant access/change credentials/accept terms/consent**, **download/execute**. Vendors converge on: confirm before state-changing actions (OpenAI), confirm before publishing/purchasing/sharing personal data (Anthropic), confirm consequential tools (`consequentialHint`, WebMCP), critic model checking goal alignment (Google). Site-side implication: such actions should be unmistakably named (button text/accessible name contains the verb), require an explicit, separate confirmation step, and never be reachable by a single ambiguous click or auto-submit (ties to WCAG 3.2.1/3.2.2 and 3.3.4 Error Prevention).

**Recommended action pattern (INFERENCE, modelled on treosh + pa11y-ci):**
1. Ship a **JS action** (`runs.using: node24`), not Docker: faster start, Playwright-installed Chromium via `npx playwright install --with-deps chromium` or reuse runner Chrome, and `actions/cache`-friendly.
2. Inputs: `urls` (newline list) **or** `sitemap`; `configPath` (JSON/TS config with per-check thresholds, same ESLint-style `off|warn|error` levels as LHCI); `budget` (minimum score 0–100); `uploadArtifacts` (default true); `failOn` (`error` | `warn` | `never`); `comment` (post/update a single sticky PR comment); `token`.

4. Exit codes: 0 pass, 1 budget/assertion failure, 2 tool/crawl error (mirrors pa11y-ci's convention of distinguishing audit failure from runtime failure).
5. Determinism: `runs: N` with `aggregationMethod: median` for behavioural metrics (CLS, timing), single run for structural checks.

## Implications for Agentic-Web-Check

**1. Deterministic (static/DOM) checks — cheap, reproducible, directly cited:**
- Agent-perception set = Lighthouse `agent-accessibility-tree` rule list (B.1 / A.2) run through `@axe-core/playwright` `withRules([...])`; score them with Lighthouse's own weights (10/7/3/1) rather than a flat pass/fail, so partial progress is visible. Core: `button-name`, `link-name`, `label`, `select-name`, `input-button-name`, `image-alt`, `document-title`, `aria-*` validity/required, `duplicate-id-aria`, `tabindex`, `autocomplete-valid`, `aria-hidden-focus`, `bypass`/`landmark-one-main`, `heading-order`, `form-field-multiple-labels`, `html-has-lang`.
- Ambiguous names: links/buttons whose accessible name is generic ("click here", "learn more", "submit") or duplicated with different hrefs (WCAG 2.4.4, WebVoyager/Online-Mind2Web grounding failures).
- Label-in-name mismatch (2.5.3): visible text ∉ accessible name → screenshot agents and tree agents disagree.
- Native vs custom controls: `<div role=combobox>`/custom date pickers without `<input type=date>` fallback, sliders without `role=slider`+`aria-valuenow`, drag-and-drop without keyboard/button alternative (WebGames/WILBUR).
- Hidden-instruction scan (C.3): text in `display:none`/`aria-hidden`/zero-size/off-screen/comment nodes containing imperative LLM-directed phrasing. Report as "injection surface", not proof of attack.
- Consequential-action labelling (C.4): forms/buttons with purchase/delete/send/transfer semantics must have explicit verb in the name, `type=submit` not auto-submit on change (3.2.1), and a confirmation step; WebMCP tools with `consequentialHint`/`readOnlyHint` set consistently with their form `method`.
- Discoverability: `llms.txt` (≥50 chars, H1, ≥1 link), `ai-catalog.json` (ARD 1.0), robots.txt AI-bot rules, sitemap — mirroring Lighthouse + Cloudflare checks so scores are comparable.
- WebMCP: registered-tools count, schema validity, form coverage (Lighthouse 13.2 audits).

**2. Behavioural tests (need a driven browser, possibly an LLM-driven agent):**
- Overlay interference: after load, is any `dialog`/cookie/consent/ad element covering the primary CTA, and is it dismissible via an element with an accessible name? (BrowserArena/GUI-Robust).
- Bot/CAPTCHA walls on first navigation and on form submit (Web Bench WRITE collapse; WCAG 3.3.8).
- Action feedback: after click/fill, does the a11y tree or URL change within N ms (GUI-Robust "Action Failure", CLS from Lighthouse agentic category).
- Lazy/infinite content: do key elements exist only after scroll; do iframes/shadow roots hide interactive elements from the top-level tree (browser-use limits).
- Keyboard-only completion of the primary flow (proxy for tree-driven agents).
- Task runs through a real agent harness (Playwright MCP / browser-use) for the site's 3–5 "golden tasks", graded by the primitives below.

**3. Evaluation primitives to adopt for task verdicts (borrow WebArena's config shape, WebCanvas's checkpoints, WebArena-Verified's rigour):**
- `url_match` with `GOLD in PRED` path+query semantics; `exact_match` / `must_include` on extracted answers with normalization-aware comparators (Verified); `program_html {url, locator, required_contents}` for DOM state; backend/API state assertions for state-changing tasks (Verified, WorkArena `validate()`).
- Intermediate **key nodes** (URL / element path / element value, exact|include|semantic) so partial credit and the failing step are reported (WebCanvas, TheAgentCompany weighted partial score).
- LLM judge only as fallback, WebJudge-style (key points → key screenshots → verdict), with the judge's reasoning stored; never the sole arbiter for WRITE tasks (BrowserArena VLM-vs-human gap, Verified hallucination finding).
- Always record a HAR/trace and the final a11y snapshot alongside the verdict so false positives can be audited.
